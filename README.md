# 电子提单控制权交接

保证电子提单控制权、运输事实和跨境支付条件始终一致。

## 领域资料

- `contracts/domain.schema.json` 规定共享领域资料结构；`fixtures/domain.json` 保存参与方、领域事实与约束。
- `contracts/events.schema.json` 规定追加式事件结构；`fixtures/events.json` 是一份可回放的全生命周期场景，每条流水都写明期望结果（生效，或应命中的规则码）。
- 当前参与方包括进出口企业、承运人、贸易融资银行、提单平台运营方。仓库不保存账号、密钥、连接串或真实身份信息，签名均为占位摘要。

## 模型

`domain/events` 用**追加式事件日志**描述交接：

- 事件只有签发、背书、运输节点、改单、拆单、合单、质押、解押、冻结、解冻、放款十一种；生效后不可覆盖、不可删除，事件之间以哈希链相连。
- 每份电子提单的**唯一现状**（签发方、当前持有人、背书序列、货物批次、运输节点、质押状态、支付条件）由事件折叠得到。
- 背书转让须双方签名；系统支持“发起提案 + 受让方会签”，会签时按当时现状重新校验，期间发生的质押/冻结会让过期指令失效。
- 承运人离线期间产生的运输节点可晚到回补：按节点序号归并进完整历史，标记为晚到事件，但**不撤销已生效的控制权**；对已拆单/合单原单的回补沿血缘传播给有效后代。
- 改单只能追加更正事件，禁止触碰持有人与批次数量；拆单、合单强制数量守恒并记录血缘。
- 质押未解除或争议冻结期间，转让与放款一律拒绝。
- 放款必须同时核对：当前控制权人 == 条件指定收款人、支付条件要求的运输节点已上报（含回补）、质押状态符合条件；支付回调按幂等键去重，无键重试再由“已放款”现状拦截。
- 被规则拒绝的尝试（旧持有人重复背书、伪造放款、重复回调等）不进入事件正文，但单独记入**拒绝台账**，供审计确认异常补偿结果。

## 三类视图

- **贸易方**（`ViewForTrader`）：只看到自己持有或曾经持有的提单，随时可见权利状态与待办（待会签、待解押、争议）。
- **银行**（`ViewForBank`）：字段白名单 + 范围限定，只读到本行质押中或本行已放款提单的履约证明，看不到背书明细等无关信息。
- **审计**（`AuditPayment`）：从任一支付动作（成功或被拒绝）出发，用事件前缀重放重建**放款时点**现状，确认当时控制权、运输事实、归并的晚到事件、血缘祖先上的异常拦截记录，并校验哈希链完整。

## 本地校验

```bash
go test ./...
```

测试回放 `fixtures/events.json` 并断言：每条流水命中期望规则码；拆合单数量守恒；旧持有人在货权转移后的背书/放款指令被拒且不污染现状；晚到回补不改写控制权；重复运输与支付回调均被幂等拦截；三视图的可见范围正确；审计能重建支付时点并发现全部攻击与补偿。
